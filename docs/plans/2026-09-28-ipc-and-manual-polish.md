### 接纳领域与职责边界
目前保留现有结构。第一阶段已经修复可观察行为并补上契约测试，本轮没有新增接纳入口，不需要立即迁移跨模块状态。

“接纳协调器”的价值应在于统一管理待处理请求、冻结策略、扫描代次、取消和启动许可，而不是机械拆分文件。控件仍属于 Qt，实际执行顺序和任务生命周期仍属于 Scheduler。

| 边界 | 负责什么 | 不能推导出什么 |
| --- | --- | --- |
| IPC 传输 | 有界认证请求、派发凭据、接纳应答 | 收到应答不代表解压成功，也不授权清理源文件。 |
| 接纳 | 已收到的路径、源身份与去重、任务清理策略快照、仍有效的启动意图 | 后续全局设置不能改写已接纳任务的清理策略。 |
| 扫描会话 | 根目录与配置快照、代次、取消、候选投递 | 作废代次的迟到候选或完成信号不能恢复任务或启动队列。 |
| Scheduler | 已登记任务身份、单个活动任务、小包优先、同大小接收顺序、人工恢复优先 | 表格排序和 UI 待处理请求不能代替调度决策。 |
| Executor | 清单、解压、校验、提交，以及独立的清理证明 | 接纳成功或推荐候选不等于可以删除源包。 |

未来确需提取时，以已有启动、取消、迟到信号和策略冻结测试为保护，逐个迁移状态转换。`_launch_scan`、`_finish_scan`、`_cancel_scan` 的代次和启动意图应由同一方管理，不能把标记分散到新类和窗口两处。协调器只决定是否接纳、何时允许启动，不负责文件清理或调度优先级。

### 已确认的排序范围
2026-09-28 用户明确：**右键多选被 Explorer 拆成多条请求时，不要求整次选择严格按“小包 → 大包”启动。** 此方向已确认，不再作为待答问题。

- 已接纳的普通待执行任务继续按源包大小升序；同大小按接收顺序，人工输入后的恢复任务优先，当前任务不被抢占。
- 保留同一次请求整批接纳、相关扫描结束后启动的现有处理；不为尚未送达的独立请求新增等待。
- 不新增跨请求收集协议、选择批次编号、收齐标记或猜测式固定延时，也不因此改变右键入口。
- 独立 Explorer 调用缺少共享选择身份和完成标记。超时只能猜测输入是否结束，不能证明批次完整；这是适用范围说明，不是尚待实现的缺陷。
